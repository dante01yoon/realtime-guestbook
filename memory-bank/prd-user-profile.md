# 사용자 프로필 기능 PRD

## 1. 개요 (Overview)

- **기능명**: 사용자 프로필 기능
- **목표**: 사용자가 자신의 정체성을 표현할 수 있도록 닉네임과 프로필 이미지를 설정하는 기능을 제공한다. 이를 통해 방명록에서 누가 글을 작성했는지 명확하게 인지하고, 커뮤니티의 유대감을 높인다.

## 2. 사용자 스토리 (User Stories)

> - **As a** 회원가입한 사용자로서,
> - **I want to** 나를 나타내는 닉네임과 프로필 사진을 등록하고 수정하고 싶다.
> - **So that** 다른 사람들이 방명록에서 나를 쉽게 알아볼 수 있다.
>
> - **As a** 방명록을 보는 사용자로서,
> - **I want to** 다른 사용자의 닉네임과 프로필 사진을 보고 싶다.
> - **So that** 누가 어떤 글을 썼는지 명확하게 알 수 있다.

## 3. 기능 요구사항 (Functional Requirements)

- **P0 (필수)**
    - 사용자는 자신의 프로필 페이지로 이동할 수 있어야 한다.
    - 프로필 페이지에서 닉네임(display_name)을 수정하고 저장할 수 있어야 한다.
    - 프로필 페이지에서 프로필 이미지(avatar_url)를 업로드하고 변경할 수 있어야 한다.
    - 방명록 목록과 상세 페이지에서 작성자의 닉네임과 프로필 이미지가 보여야 한다.
    - 회원가입 시, `auth.users` 테이블에 사용자가 생성되면, `profiles` 테이블에도 해당 사용자의 초기 프로필 정보가 자동으로 생성되어야 한다. (트리거나 서버 API 사용)
- **P1 (다음 순위)**
    - 닉네임은 중복될 수 없다.
    - 프로필 이미지 업로드 시, 용량 제한(예: 5MB)을 둔다.
- **P2 (고려)**
    - 사용자가 자신의 프로필 페이지에서 과거에 작성한 글 목록을 볼 수 있다.

## 4. 비기능 요구사항 (Non-functional Requirements)

- **데이터베이스**: `profiles` 테이블에 `id(PK, FK to auth.users.id)`, `display_name(text)`, `avatar_url(text)` 컬럼이 필요하다.
- **보안**: 사용자는 오직 자신의 프로필 정보만 수정할 수 있어야 한다. (`profiles` 테이블에 RLS 정책 `auth.uid() = id` 적용)
- **성능**: 프로필 이미지 로딩 속도가 너무 느리지 않도록 적절한 최적화(예: 이미지 리사이징, 캐싱)를 고려한다. (이번 단계에서는 Supabase Storage 기본 기능을 사용)

# 대댓글 및 좋아요 기능 PRD

## 1. 개요 (Overview)

- **기능명**: 대댓글 및 좋아요 기능
- **목표**: 사용자들이 기존 댓글에 대해 직접 답글을 달거나 '좋아요'로 반응할 수 있게 하여, 보다 다층적이고 활발한 소통이 이루어지는 커뮤니티를 만든다.

## 2. 사용자 스토리 (User Stories)

> - **As a** 사용자로서,
> - **I want to** 특정 댓글에 직접 답글을 달고 싶다.
> - **So that** 원래 댓글의 맥락 안에서 대화를 명확하게 이어갈 수 있다.
>
> - **As a** 사용자로서,
> - **I want to** 마음에 드는 댓글에 '좋아요'를 누르고 싶다.
> - **So that** 글을 쓰지 않고도 간편하게 공감이나 지지를 표현할 수 있다.
>
> - **As a** 사용자로서,
> - **I want to** 내가 누른 '좋아요'를 다시 눌러 취소하고 싶다.
> -   **So that** 실수로 눌렀거나 마음이 바뀌었을 때 되돌릴 수 있다.
>
> -   **As a** 사용자로서,
> -   **I want to** 각 댓글이 받은 '좋아요' 개수를 보고 싶다.
> -   **So that** 어떤 의견이 많은 사람들의 공감을 얻고 있는지 알 수 있다.

## 3. 기능 요구사항 (Functional Requirements)

-   **대댓글 (P0 - 필수)**
    -   각 댓글 아래에 '답글 달기' 버튼이 표시되어야 한다.
    -   '답글 달기' 버튼을 클릭하면, 해당 댓글 아래에 대댓글을 입력할 수 있는 폼이 나타난다.
    -   작성된 대댓글은 부모 댓글 아래에 시각적으로 들여쓰기(Indentation) 되어 표시되어야 한다.
    -   대댓글에도 작성자 정보(프로필 사진, 닉네임)와 작성 시간이 표시되어야 한다.
-   **좋아요 (P0 - 필수)**
    -   각 댓글(및 대댓글) 영역에 '좋아요' 아이콘(예: 하트)과 현재 '좋아요' 수가 표시되어야 한다.
    -   로그인한 사용자는 '좋아요' 아이콘을 클릭할 수 있다.
    -   사용자가 '좋아요'를 누르면, 아이콘의 색상이 바뀌고 '좋아요' 수가 실시간으로 1 증가한다.
    -   이미 '좋아요'를 누른 댓글에 다시 아이콘을 클릭하면, '좋아요'가 취소되고 아이콘 색상과 숫자가 원래대로 돌아온다.
    -   한 사용자는 하나의 댓글에 한 번만 '좋아요'를 누를 수 있다 (토글 방식).
-   **P1 (다음 순위)**
    -   대댓글에 대한 대댓글(2단계 이상 깊이) 기능 지원을 고려한다.
    -   '좋아요' 아이콘에 마우스를 올리면 누가 '좋아요'를 눌렀는지 일부 사용자 목록을 보여준다.

## 4. 비기능 요구사항 (Non-functional Requirements)

-   **데이터베이스**:
    -   **대댓글**: `comments` 테이블에 `parent_id` 컬럼(자기 자신 테이블의 `id`를 참조하는 외래 키)을 추가하여 부모-자식 관계를 표현한다. `parent_id`가 `NULL`이면 일반 댓글, 값이 있으면 대댓글로 구분한다.
    -   **좋아요**: `comment_likes` 테이블을 신규 생성한다. `comment_id`와 `user_id`를 복합 기본 키(Composite Primary Key)로 사용하여, 어떤 사용자가 어떤 댓글에 '좋아요'를 눌렀는지 기록한다. 이를 통해 중복 '좋아요'를 방지한다.
-   **보안**:
    -   로그인한 사용자만 대댓글을 작성하거나 '좋아요'를 누를 수 있도록 RLS 정책을 설정한다.
-   **성능**:
    -   방명록 글을 불러올 때, 관련된 댓글, 대댓글, 좋아요 수를 효율적으로 함께 조회할 수 있도록 쿼리를 최적화한다.
