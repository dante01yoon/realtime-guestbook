# Supabase는 만능일까? | 초심자를 위한 고찰과 유의사항

Supabase는 백엔드 개발의 복잡성을 극적으로 낮춰주는 BaaS(Backend as a Service) 솔루션입니다. 데이터베이스, 사용자 인증, 실시간 구독, 스토리지 등을 하나의 플랫폼에서 제공하여, 특히 프런트엔드 개발자나 1인 개발자가 아이디어를 빠르게 현실로 만들 수 있도록 돕습니다.

하지만 이 강력한 도구를 사용할 때, 우리는 그 편리함 뒤에 숨겨진 책임과 원리를 이해해야만 합니다. 이 글에서는 Supabase가 '만능'이 아닌 이유와, 초심자가 반드시 유의해야 할 사항들을 알아봅니다.

## Supabase가 만능처럼 보이는 이유

-   **All-in-One 플랫폼**: 별도의 서버 코드 없이 데이터베이스(PostgreSQL), 인증, 파일 스토리지, 엣지 함수를 모두 사용할 수 있습니다.
-   **뛰어난 개발 경험**: 클라이언트 라이브러리(`supabase-js`)가 매우 직관적이어서, 프런트엔드에서 데이터베이스를 직접 제어하는 듯한 경험을 제공합니다.
-   **실시간 기능 기본 탑재**: 별도의 설정 없이 데이터베이스 변경 사항을 실시간으로 구독할 수 있어, 채팅이나 협업 툴 같은 기능을 쉽게 구현할 수 있습니다.
-   **오픈소스 기반**: 특정 벤더에 종속될 걱정이 적고, 원한다면 직접 호스팅(Self-hosting)할 수도 있습니다.

이러한 장점들 덕분에 개발 속도는 비약적으로 향상되고, 인프라 관리 부담은 크게 줄어듭니다. 하지만 바로 이 지점에서 첫 번째 경고등이 켜집니다.

## 초심자를 위한 경고 및 유의사항

### 1. "쉽다"는 말의 함정: RLS는 자동이 아니다

Supabase의 가장 중요하고도 위험한 기능은 단연 **RLS(Row-Level Security)** 입니다.

-   **경고**: Supabase는 **"기본적으로 안전하게(Secure by default)"** 설계되었습니다. RLS가 활성화된 테이블은 **명시적인 허용 정책(Policy)이 없으면 아무도 접근할 수 없습니다.** 많은 초심자들이 테스트를 위해 RLS를 비활성화하거나 모든 접근을 허용(`true`)하는 정책을 추가하고 그대로 프로덕션에 배포하는 실수를 저지릅니다.
-   **유의사항**:
    -   **RLS는 학습 곡선이 있습니다.** 단순히 켜고 끄는 기능이 아니라, "로그인한 사용자는 자신의 글만 수정할 수 있다 (`auth.uid() = user_id`)" 와 같이 SQL 기반의 정교한 규칙을 작성해야 하는 영역입니다.
    -   **모든 테이블에 RLS를 활성화하고, 최소한의 권한만 부여하는 것을 원칙으로 삼아야 합니다.** 애플리케이션의 모든 데이터 접근 시나리오를 RLS 정책으로 방어할 수 있다는 생각으로 설계해야 합니다.

### 2. 당신은 여전히 PostgreSQL 위에서 작업하고 있다

-   **경고**: `supabase-js` 라이브러리가 너무 편리한 나머지, 자신이 순수한 PostgreSQL 데이터베이스를 사용하고 있다는 사실을 잊기 쉽습니다. 서비스가 복잡해지면 단순한 `select`, `insert`만으로는 한계가 오고, 성능 문제가 발생하기 시작합니다.
-   **유의사항**:
    -   **데이터베이스 설계의 중요성**: 테이블 정규화, 인덱싱(Indexing), 외래 키(Foreign Key) 설정 등 전통적인 데이터베이스 설계 원칙은 Supabase에서도 동일하게 중요합니다. 잘못된 설계는 나중에 큰 기술 부채로 돌아옵니다.
    -   **SQL은 당신의 친구**: 복잡한 데이터 조인(JOIN), 집계 함수, 뷰(View), 데이터베이스 함수(RPC) 등은 결국 SQL을 통해 해결해야 합니다. Supabase를 잘 쓴다는 것은 PostgreSQL을 잘 이해한다는 것과 같습니다.

### 3. 클라이언트에서 모든 것을 하려는 유혹

-   **경고**: 프런트엔드에서 Supabase API를 직접 호출하는 방식은 매우 편리하지만, 모든 비즈니스 로직을 클라이언트에 두는 것은 보안에 취약하고 유지보수를 어렵게 만듭니다.
-   **유의사항**:
    -   **민감한 로직은 서버로**: 결제 처리, 외부 API와의 연동 중 민감한 키가 필요한 작업, 복잡한 데이터 검증 등은 반드시 **엣지 함수(Edge Functions)**나 별도의 서버에서 처리해야 합니다.
    -   **`service_role_key`의 절대 원칙**: `anon_key`는 브라우저에 노출되어도 안전하지만, RLS 정책을 무시하는 막강한 권한의 `service_role_key`는 **절대로, 절대로 클라이언트 코드에 포함해서는 안 됩니다.**

### 4. RLS 정책, 많아지면 관리가 어렵다

-   **경고**: 애플리케이션 초기에는 RLS 정책이 몇 개 되지 않아 직관적입니다. 하지만 기능이 추가되고 사용자 역할(예: 일반 사용자, 관리자, 매니저 등)이 복잡해지면서 RLS 정책의 수는 기하급수적으로 늘어날 수 있습니다. 수십 개의 정책이 서로 얽히기 시작하면 전체 보안 규칙을 한눈에 파악하기 어렵고, 수정 하나가 예상치 못한 사이드 이펙트를 낳을 수 있습니다.
-   **유의사항**:
    -   **정책을 코드로 관리**: Supabase 대시보드에서 정책을 하나씩 클릭하여 만드는 방식은 테스트나 초기 개발에는 편리하지만, 장기적으로는 위험합니다. `supabase/schema.sql`과 같이 SQL 파일로 정책을 작성하고 버전 관리 시스템(Git)으로 추적해야 합니다.
    -   **로직 재사용**: 복잡하고 반복적인 검증 로직은 PostgreSQL의 함수(Function)로 만들어 여러 RLS 정책에서 호출하여 재사용하는 것이 유지보수에 유리합니다.
    -   **정책 테스트의 어려움**: RLS 정책은 테스트하기가 까다롭습니다. 데이터베이스 테스트 프레임워크(`pgTAP` 등)를 도입하거나, 다양한 사용자 역할로 직접 테스트하는 절차를 마련해야 합니다.

### 5. "무료"는 영원하지 않다: 비용 구조 이해하기

-   **경고**: Supabase의 관대한 무료 티어(Free Tier)는 프로젝트를 시작하기에 더할 나위 없이 좋지만, 사용량이 늘어나면 예상치 못한 비용이 발생할 수 있습니다. 특히 트래픽이 급증하는 경우, egress(데이터 전송량), 데이터베이스 크기, 스토리지 용량 등이 모두 비용과 직결됩니다.
-   **유의사항**:
    -   **비용 계산기 활용**: 본격적인 서비스 런칭 전, Supabase 공식 홈페이지의 비용 계산기(Pricing Calculator)를 통해 예상 사용량에 따른 비용을 반드시 시뮬레이션해야 합니다.
    -   **사용량 모니터링**: Supabase 대시보드의 Usage 리포트를 주기적으로 확인하고, 특정 임계값이 넘으면 알림을 받을 수 있도록 Billing Alert를 설정하는 것이 중요합니다.
    -   **쿼리 최적화**: 불필요하게 많은 데이터를 요청하는 비효율적인 쿼리는 egress 비용을 증가시키는 주범입니다. 필요한 컬럼만 `select`하고, 페이지네이션(Pagination)을 적극적으로 활용하여 데이터 전송량을 줄여야 합니다.

## 결론: Supabase는 '마법 지팡이'가 아닌 '최고급 연장'이다

Supabase는 의심할 여지 없이 현대 웹 개발의 패러다임을 바꾼 혁신적인 도구입니다. 하지만 그것은 개발자의 책임을 면제해주는 마법이 아닙니다. 오히려 개발자가 데이터베이스와 보안의 기본 원리를 더 깊이 이해하고 올바르게 사용했을 때 비로소 그 진정한 힘을 발휘하는 '최고급 연장'에 가깝습니다.

초심자라면 Supabase의 편리함을 마음껏 누리되, 그 이면의 RLS, PostgreSQL, 그리고 서버-클라이언트 역할 분담의 원리를 꾸준히 학습해야 합니다. 그럴 때 Supabase는 당신의 가장 든든한 파트너가 되어줄 것입니다.
